# Schema 清理原则

从 neolyst Supabase schema 重构（2026-04）中提炼。旧 schema 从 live DB OpenAPI 推断，无约束、无 RLS、无注释；新 schema 通过 22 个迁移文件重建。

核心认识：Supabase 架构下没有应用层兜底，schema 的每个缺陷都是对外的 API 缺陷。因此清理标准不是"能跑就行"，而是"每个元素都经得起为什么存在的追问"。以下原则适用于后续的 schema 设计和迁移编写。

## Schema 是契约，不是存储定义

Supabase/PostgREST 架构下，schema 即 API、即文档、即权限系统、即校验器。没有中间层可以遮盖 schema 的缺陷。

| 缺陷类型 | 传统架构 | Supabase 架构 |
|---|---|---|
| 缺约束 | 应用层兜底 | 脏数据直接入库 |
| 权限不精确 | 中间件过滤 | RLS 是唯一防线 |
| 表结构冗余 | DAO 封装隐藏 | PostgREST 直接暴露 |
| 错误消息不友好 | 应用层翻译 | RAISE EXCEPTION 即用户所见 |
| 缺注释 | 独立 API 文档 | COMMENT 即文档 |

结论：schema 的容错率为零，每个元素都必须说真话。

## 三层清理原则

### 消除欺骗

schema 声明存在的东西必须真的在使用、真的被约束、真的有含义。

- 存在但不用的表 → 删除（chief_approve、rqc_approve、report_push_log）
- 存在但永远为空的字段 → 删除（ads_conversion_factor、index_code）
- 声明但未强制的约束 → 加 CHECK/触发器（状态枚举、层级规则）
- 存在但未执行的权限 → 加 RLS
- 存在但未说明的语义 → 加 COMMENT

### 消除冗余

同一个规则只允许一个定义处。两处定义迟早不一致，不一致就是 bug。

- 路径规则只在 SQL 函数里定义，Python 不拼路径
- 状态机只在 `report_status_is_valid()` 里定义，触发器/RLS/RPC 都引用它
- 分析师身份只用 `analyst.email`，不同时在 `analyst.id` 上建第二套引用
- 权限只在 RLS 里定义，RPC 不重复校验（SECURITY DEFINER 是最后手段）

### 消除意外

每个状态转换必须显式、经过完整校验、不可绕过。

- 非对称 RLS（USING ≠ WITH CHECK）：能看到 submitted 行，但更新后必须变为 draft
- 强制撤回路径：rejected → draft → submitted，不允许 rejected 直接跳 submitted
- 全量校验：`validate_report` 收集所有错误一次性抛出，不让用户修一个跑一次

## 判断方法

### 间接层有回报吗？

| 场景 | 决策 |
|---|---|
| 分析师引用（email 直接可读） | 删除 UUID 代理键，用 email 做 PK |
| report 的分析师列表（跟随 report 生死） | 删除中间表，内联为 `text[]` |
| coverage 的分析师列表（独立生命周期） | 保留中间表 |

判断标准：**它有独立的生命周期吗？** 没有 → 内联。有 → 保留。

### 字段自证存在

每个字段必须回答"谁在什么场景下需要它"。不能回答的，删除。

- 文件名可从路径派生 → 删除 `*_file_name`
- 审批是流程不是实体属性 → 从 coverage 移除 `approved_by/at`
- author_order 已隐含主次 → 删除 `role`

### 字典表用自然键

rating、region、report_type 等低行数字典表，用业务标识做 PK（code、rank、report_type），不额外加 UUID 代理键。减少 JOIN 层级，FK 直接可读。

## 迁移策略

### 骨架先定型，RPC 后迭代

前 5 个迁移（000→040）定义 schema 结构，后续迁移只改 RPC 和 RLS。schema 一次定型，业务规则通过重写函数逐步校准。

### 权限只能收紧

先建基本 RLS，再通过迁移逐步收紧。发现 edge case 就加迁移，不回过头改已执行的迁移文件。

### 错误消息面向最终用户

RAISE EXCEPTION 的消息直接传到前端。用中文写，不用英文。所有异常消息统一在最后一个迁移里批量中文化。

## 投机性设计的识别

旧 schema 中有三张表是投机性设计：`chief_approve`、`rqc_approve`、`report_push_log`。它们对应的功能从未实现，但表的存在误导了开发者。

识别标准：**这张表对应的 UI 流程走通了吗？** 走不通 → 删除。保留它会让人以为功能已实现。

## 底层认知

### 存储优先 vs 契约优先

旧 schema 是存储优先的思维：需要持久化什么数据就加什么表和字段。新 schema 是契约优先：schema 是系统对外做出的承诺，每个元素都代表一条可执行的保证。

| 思维 | 关注点 | 遗留问题 |
|---|---|---|
| 存储优先 | "数据放哪" | 字段在但没人用，表在但没功能，约束声明了但不强制 |
| 契约优先 | "我承诺什么" | 每个元素要么在兑现承诺，要么删除 |

旧 schema 的问题不是"设计得不好"，而是"说了不算"。有字段但不用、有约束但不强制、有权限但不执行——这些都是系统在撒谎。

### 模糊性的代价

Supabase 架构下，schema 的每一个模糊点都会变成前端开发者的猜测题：

- status 可以为 null 吗？schema 没说 → 前端猜一个
- 报告可以没有分析师吗？没有约束 → 前端猜一个
- 谁能看到 submitted 状态的报告？RLS 没写 → 前端猜一个

猜测会发散。两个前端开发者猜出两个不同的答案，系统行为就不一致。CHECK、RLS、COMMENT 的作用不是"加强设计"，而是**消除猜测空间**，让每个问题的答案在 schema 里只有一个。

### 表面规则的统一来源

三层清理原则（消除欺骗、消除冗余、消除意外）不是三条独立的规则，而是同一条原则的三个面：

> **schema 中的每个元素都必须精确反映系统的真实状态。**

- 存在但不用 → 不反映真实状态 → 消除欺骗
- 两个定义不一致 → 不知道哪个反映真实状态 → 消除冗余
- 用户能到达未预期的状态 → schema 没反映真实的业务约束 → 消除意外

### 迁移序列暴露的方法论

22 个迁移不是随机排列的，它们展示了一个可复用的工作方法：

1. **定契约**（000→040）：表结构、约束、RLS、注释。一次成型，后续不改结构。
2. **建流程**（045→070）：为每个用例写 RPC。路径规则、状态流转、数据校验。
3. **用起来发现问题**（080→100）：使用中发现 edge case（rejected 要重提、analyst 要看 published、版本号应该 DB 侧读）。
4. **收紧**（105→114）：堵住发现的漏洞。撤回权限、非对称 RLS、全量校验、中文错误消息。
5. **演化**（p1_iter_a）：理解加深后，进一步简化结构（删表、内联字段）。

这个顺序不是偶然的。它说明 schema 设计不是"先想清楚再动手"，而是"先建骨架，再通过使用逐步校准"。但校准的颗粒度有区别：**结构调整只做一次，RPC 和 RLS 可以反复迭代**。

### 自然键的适用边界

analyst 用 email 做 PK、region 用 code 做 PK，这不是"自然键比代理键好"的教条，而是一个具体的取舍：

- 系统规模小，email/code 在业务语义上确实稳定不变
- 这些键的可读性收益（少 JOIN、FK 直接可读）在 Supabase/PostgREST 场景下尤其大——前端开发者看 `analyst_email` 就知道是谁，不需要再查一次 analyst 表
- 如果键值可能变化（比如用户改邮箱），自然键的代价会超过收益，那时用 UUID 更安全

结论：自然键的判断标准不是"这个值是否唯一"，而是"这个值是否足够稳定，以至于用它做 FK 的可读性收益超过变更风险"。

### COMMENT 不是文档，是接口规格

在传统系统里，数据库注释是锦上添花的文档。在 Supabase 里，COMMENT 是 API 接口规格的一部分——PostgREST 可以暴露注释给消费者。写 COMMENT 的标准不是"解释实现细节"，而是"告诉消费者这个字段承诺什么"。

例如 `report.status` 的 COMMENT 写的是"合法值：draft、submitted、published、rejected"，而不是"用 CHECK 约束限制了四个值"。前者是契约，后者是实现。

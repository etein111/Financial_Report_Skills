# DOCSTR

## 1. 这个标准是针对谁的

本标准针对正在阅读、修改或调用某个具体函数、类、模块入口的开发者。

它服务于这样的场景：

- 已经定位到具体实现单元，需要理解这段代码到底做什么
- 准备修改函数行为，需要先确认输入、输出和副作用
- 需要避免误用某个函数，或避免破坏某段局部机制
- 需要快速知道这段代码为什么这样写，以及改动时应注意什么

DOCSTR 不是目录导航，也不是子系统总说明。

## 2. 基本原则

- 只写贴着具体实现单元才有意义的说明
- 只写单个函数、类或模块入口自身的规则
- 主要作用是说明“这段代码做什么、怎么做、有什么限制”
- 代码实现一旦变化，这些说明通常也要同步变化
- 优先写会导致误用、误改、误判的局部信息
- 不写跨模块的目录地图和维护入口
- 不写已经由 README 负责的模块分工和运行说明
- 不复述代码表面可直接看出的机械过程，重点写意图、约束、副作用和边界

## 3. 具体都放什么内容

- 功能说明：这个函数、类或模块入口负责什么，不负责什么
- 输入语义：参数的含义、前置条件、允许为空或必须满足的条件
- 输出语义：返回值的含义、成功时保证什么
- 副作用：是否写库、写文件、改状态、发请求、上传下载等
- 执行要点：必要时说明关键步骤或顺序，但只限本实现单元内部
- 局部约束：这段实现依赖哪些前提，不能省略哪些检查
- 错误语义：会在什么情况下失败，失败时抛什么类型或什么性质的错误
- 边界说明：哪些事情由调用方负责，哪些事情本实现不会做
- 兼容性说明：与当前实现方式强绑定、未来可能变化但现在必须遵守的局部约束
- 修改提示：维护这段代码时最容易破坏的点是什么
- 必要示例：只有在不用示例就容易误用时，才放最小示例

# **分析师报告自动化处理系统 (需求与设计文档)**

**导读**：本文档同时包含需求与设计。第 1\~2 节描述业务目标与操作流程，供业务人员与项目经理阅读；第 3\~4 节描述目录结构、核心文件与技术方案，供研发落地参考。

## **1\. 系统概述与设计目标**

本项目旨在建设一套面向分析师报告的自动化生产能力，提升模板维护、草稿解析和标准报告生成的效率。

🎯 **核心设计目标：业务人员自主配置与管理**

本系统允许业务人员通过自然语言维护提取规则和排版模板。YAML 文件作为系统生成的可读资产保留在仓库中，便于查阅与审计，但第一版不要求业务人员手工修改这些文件。

## **2\. 核心工作流（业务人员操作指南）**

系统以对话框（Chat UI）为主要交互界面，用户通过文件上传和自然语言指令完成核心工作。系统包含两个场景：

### **场景一：报告模板的制作与维护**

**业务痛点**：新增或修改模板通常依赖研发介入，响应慢、维护成本高。

* **步骤 1：上传标准样本**  
  用户提供一份排版标准的历史报告（Word）以及对应的要素清单（elements.yaml），上传至系统并输入指令（如：“将其设为 common 模板”）。  
* **步骤 2：系统自动构建与验证**  
  系统解析 Word 模板，将动态内容替换为占位符，并基于原要素执行一次闭环验证。验证通过后，提示模板创建成功。  
* **步骤 3：对话式修改提取规则与模板联动**  
  当业务需要新增字段（如需要提取“风险提示”）时，**业务人员无需手动改代码，直接在对话框告诉 AI**：“以后提取宏观报告时，增加一个‘风险提示’字段”。  
  系统收到指令后会生成变更计划，并默认先展示预览：  
  1. 自动在后台更新提取规则文件（schema.yaml）。  
  2. 自动修改模板 Word，在目标位置插入或替换占位符。  
  3. 向用户展示变更摘要；若用户明确要求“直接应用”，则可跳过确认。  
* **步骤 4：模板排版生效**  
  用户确认后，系统更新正式模板并执行一次最小渲染验证。验证成功后，新规则与模板同时生效。

### **场景二：分析师日常报告生成**

**业务痛点**：分析师草稿格式不统一，后期人工排版耗时。

* **步骤 1：提交草稿**  
  分析师将撰写完成的报告草稿（无需关注排版格式）上传至系统，输入指令（如：“生成标准排版报告”）。  
* **步骤 2：智能解析与结构化提取**  
  系统识别报告类型，通过 `router.yaml` 路由到对应模板，提取草稿中的文本、图表及核心要素，并为该报告创建独立目录保存处理结果。  
* **步骤 3：核心数据确认**  
  系统在对话框中展示提取出的关键要素信息。若有遗漏或错误，分析师可通过自然语言指令直接要求系统进行修改更新。第一版中，系统在此阶段暂停，等待 Editor 确认后再进入最终生成。若需切换模板，只允许在该确认阶段进行。  
* **步骤 4：标准报告生成**  
  数据确认无误后，系统结合对应模板渲染并输出标准 Word 和 PDF。第一版中，摘要与正文分别保存为可直接打开检查的 Word 片段，再与模板合并生成最终文档。

## **3\. 架构与目录拓扑 (Agent Skills Architecture)**

以下内容为研发落地指南，基于 Anthropic Agent Skills 开放标准构建。

### **3.1 核心数据文件词典 (YAML + Word 的业务友好设计)**

系统以 YAML 作为核心结构化配置格式，并以 Word 文件承载模板与长文本内容，兼顾可读性与版式稳定性：

1. **elements.yaml (统一业务要素单)**：  
   * 用于记录结构化业务数据（如 `company: 西锐飞机`）。既可作为模板样本输入，也可作为草稿解析后的落盘结果。  
2. **schema.yaml (提取规则说明书)**：  
   * 用于记录字段定义、描述和提取要求。该文件由 AI 通过对话自动维护，业务人员需要时也可以直接查阅。
3. **router.yaml (模板路由表)**：  
   * 用于维护“报告类型 -> 模板名”的静态映射。第一版只做静态路由，不引入关键词、作者或语言等复杂匹配规则。多个报告类型可映射到同一模板，例如 `macro`、`quant` 可共用 `common` 模板。  
4. **meta.yaml (轻量元数据文件)**：  
   * 用于记录模板或报告的基础说明信息，例如名称、状态、更新时间和所用模板。  
5. **template.docx / abstract.docx / body.docx (Word 资产文件)**：  
   * `template.docx` 为正式排版模板；`abstract.docx` 与 `body.docx` 为从草稿中拆出的可直接打开检查的 Word 片段。第一版保留 Word 形态，暂不引入 Markdown 中间层。

### **3.2 目录拓扑结构**

系统严格区分“技能插件”“正式模板资产”和“每篇报告的处理现场”。目录保持扁平，便于 Editor 检查与维护。第一版不引入 `workspace`、`jobs`、`versions` 等额外层级，也不保留模板修改历史目录。

/agent\_workspace/  
│  
├── /skills/                            \<-- \[Agent Skills 插件区\]  
│   ├── /template-maker/                \<-- 技能 1：模板制作与维护  
│   │   └── SKILL.md                      
│   └── /report-maker/                  \<-- 技能 2：报告生成与验证  
│       └── SKILL.md                      
│  
├── /templates/                         \<-- \[正式模板资产区\]  
│   ├── router.yaml                     \<-- 报告类型到模板名的静态映射  
│   └── /common/                        \<-- 模板目录按“模板名”组织，而非按报告类型组织  
│       ├── schema.yaml                 \<-- 提取规则说明书  
│       ├── template.docx               \<-- 正式排版模板  
│       └── meta.yaml                   \<-- 模板基础信息  
│  
└── /reports/                           \<-- \[每篇报告的处理现场\]  
    └── /西锐飞机首次覆盖报告/  
        ├── draft.docx                  \<-- 原始草稿  
        ├── elements.yaml               \<-- 提取出的结构化要素  
        ├── abstract.docx               \<-- 摘要 Word 片段  
        ├── body.docx                   \<-- 正文 Word 片段  
        ├── /assets/                    \<-- 图表/截图等复杂资产  
        ├── output.docx                 \<-- 标准排版输出  
        ├── output.pdf                  \<-- PDF 发布版  
        └── meta.yaml                   \<-- 报告基础信息与状态  

补充约束：

* `skills/` 只存放符合 Agent Skills Open Standard 的技能插件，不存放正式模板。  
* `templates/` 只存放正式模板资产；第一版模板目录按“模板名”组织，避免与报告类型强绑定。  
* `reports/` 的子目录按“报告名”组织，而非按任务 ID 组织。目录名应尽量规整，去掉无用前后缀，便于 Editor 直接定位和检查。  
* 第一版模板修改频率低，因此不单独设计模板工作目录；候选文件或临时产物可在运行时临时目录中处理，验证通过后再覆盖正式模板。  

### **3.3 Skills 边界与职责**

两个 skills 的边界按写权限划分，而不是按功能感觉划分：

1. **template-maker**
   * 只负责 `templates/` 目录下的正式模板资产。  
   * 职责包括：创建和维护 `template.docx`、`schema.yaml`、模板 `meta.yaml`，维护 `router.yaml`，以及在模板修改后执行一次最小渲染验证。  
   * 不负责处理单篇报告，也不写入 `reports/`。  

2. **report-maker**
   * 只负责 `reports/` 目录下的单篇报告处理现场。  
   * 职责包括：接收草稿、识别报告类型、选择模板、生成 `reports/<report_name>/`、抽取 `elements.yaml`、生成 `abstract.docx`、`body.docx`、`assets/`，并在确认后生成 `output.docx` 和 `output.pdf`。  
   * 不负责修改正式模板，不负责写 `schema.yaml`、`router.yaml` 或模板目录下的其他资产。  

3. **report-maker 的两阶段流程**
   * 第一阶段为“抽取与确认”：系统先抽取要素与文档片段，生成报告目录并等待 Editor 检查和修正。  
   * 第二阶段为“渲染与输出”：只有在确认完成后，系统才进入最终渲染并输出标准报告。  
   * 模板切换只允许在第一阶段进行；一旦进入最终渲染阶段，不再支持切换模板。  

## **4\. 关键技术栈 (Tech Stack)**

本系统第一版采用以下技术方案：

1. **模板引擎 (短数据合并)**：  
   * 采用 **python-docx-template** (基于 Jinja2)，将 `elements.yaml` 中的短文本数据直接渲染到 Word 模板中的独立占位符。  
2. **文档片段处理引擎 (第一版以 Word 为中心)**：  
   * 第一版不引入 Markdown 中间层，而是直接从草稿中拆出 `abstract.docx` 与 `body.docx` 两个可检查的 Word 片段。  
   * 最终渲染时，短字段通过占位符合并，长文本以 Word 子文档或等价方式并入主模板，优先保证版式稳定与人工可检查性。  
3. **结构化抽取引擎 (语义理解)**：  
   * 基于大语言模型 (LLM) 的语义理解能力，结合 `schema.yaml` 的约束，从原始 Word 草稿及拆分后的文档片段中抽取业务数据。  
   * 第一版中，该抽取能力作为 `report-maker` 的前半段职责存在，不额外拆分为第三个 skill。  
4. **复杂资产高保真提取 (PDF 坐标裁剪法)**：  
   * 对草稿中的复杂图表和财务模型表格，采用“隐藏转 PDF + 高清裁图”方案。  
   * 先用 LibreOffice 将原始 Word 草稿转为高质量 PDF，再用 **PyMuPDF (fitz)** 识别目标区域并截图裁剪，结果存入 `assets/`。该方案优先保证视觉保真，避免复杂表格在结构化转换中失真。  
5. **最终发布格式转换**：  
   * 采用 **libreoffice \--headless** 命令，在 Linux 或容器环境中将渲染完成的 Word 终稿转换为 PDF 发布版。

# 零、STAR 总览

```
第一段 = S 现状 + T 任务 + A 架构与技术内核 + R 效率（小时 → 分钟）
第二段 = A 工程实现 + R 质量与扩展（可信 · 能长大）
```

**第一段回答"快不快"，第二段回答"稳不稳、能不能长大"。**

### 第一段

| 句 | 内容 | STAR |
|---|---|---|
| 1 | 券商研报"自由格式→合规标准"的生产难题 | **S + T** |
| 2 | 三个可协作 Agent Skill | A · 架构第一步 |
| 3 | 任务路由与工具调用编排 / 9 类报告 | A · 编排 |
| 4 | 两阶段管线：LLM 抽取字段 + 定位内容块 | A · 技术内核 |
| 5 | 格式执行 + 幻觉隔离 | A · 技术内核 |
| 6 | 渲染后校验 + 人工确认 + 小时→分钟 | A 验证 + **R** |

**关键结构判断**：
- 句 1 只承担 S 和 T，**不在这一句讲方案**——先让面试官进入问题，再给方案
- **R 必须放在最后**，紧跟"验证"之后。先给数字再讲怎么验，数字不可信

### 第二段

| 句 | 内容 | STAR |
|---|---|---|
| 1 | 全链路质量治理 + 自研取舍 | A · 总起 |
| 2 | 深层嵌套突破 / 理解层上下文 / 渲染后校验 | A · 工程细节（文档维度） |
| 3 | 状态机固化数据库层 / 拒绝非法流转 / 自动审计 | A · 流程约束 |
| 4 | 三层权限 + 模板运行时解析 | A · 权限与配置 |
| 5 | 测试与评估 / 可复用组件 / 规模化 | **R** |

第二段里唯一一句后端功底的话，面试官用它判断你是「会写 Python 的」还是「懂系统的」。

# 第一章 · 第一段逐句深挖

> 原文：
> 针对券商投研报告"自由格式草稿→合规标准格式"的生产难题，基于 OpenCode 智能体框架，设计 3 个可协作 Agent Skill（Template Maker / Report Maker / Neolyst），以任务路由与工具调用编排"模板制作→内容生成→审核入库"全流程，支撑 9 类中英文报告自动生成。核心为"LLM 理解 + 确定性兜底"两阶段管线：LLM 依 Schema 从非结构化草稿抽取 25+字段并定位内容块，格式执行交由确定性代码兜底，将幻觉隔离在可校验的理解层，配合渲染后校验与人工确认形成"理解—执行—验证"闭环，单份报告产出由小时级降至分钟级。

## 句 1｜针对券商投研报告"自由格式草稿→合规标准格式"的生产难题

### 面试口语稿

> "我先说清楚我做的是什么问题。券商研报不是普通文档，它是**监管产品**——评级、目标价、分析师牌照编号、法律披露附录，缺一个就是合规事故。但分析师写草稿的时候是完全自由的，他打开 Word 想到哪写到哪，表格想嵌几层嵌几层。
>
> 我们原来的流程是：分析师交草稿 → 排版同事手工往合规模板里搬 → 校对 → 提给审批人。一篇公司报告搬一次要几个小时，而且出来的错**全是机械性的**：数据漏填、法律附录整段被吃掉、分节符错乱导致后半篇的页眉页码全崩。
>
> 所以我要解决的不是'写得不好'，是'**搬得不对**'。"

### 知识点深挖

**合规模板的结构原理**：研报模板靠**分节符**把文档切成若干节——封面、正文、英文摘要、法律附录各一节，每节有自己的页眉页脚、页码起始、页边距。手工搬运时动一个分节符，后面所有节的页眉页码会连锁崩掉。

> **难点不在文字，在结构。**

**研报的合规硬要求（要能一条条报出来）**：

| 硬要求 | 内容 | 缺了会怎样 |
|---|---|---|
| 法律披露附录 | 免责声明 / 利益冲突披露，独立分节 | 合规事故，报告不能发 |
| 分析师认证 | 每位署名分析师的牌照编号 | 合规事故 |
| 评级 | 买入/持有/卖出，须对应目标价 | 误导客户 |
| 目标价 + 当前价 + 日期 | 三个数字必须自洽 | 误导客户 |
| 格式结构 | 封面/正文/英文摘要/附录四节，页眉页脚页码规定死 | 排版崩坏 |

**"自由格式"是关键前提**：草稿会合并单元格、粘截图、中途改样式、留批注——**没有任何结构保证**。所以不能靠"约定格式"解析，**只能靠"理解"去读懂它**。这一句为后面"为什么必须上模型"埋了伏笔。

### 为什么这么设计

把问题定义成「**内容理解** + **格式执行**」两件事，而不是「用 AI 写研报」。这个定义决定了整个系统里模型的职责边界只能是理解，不能碰排版。

### 追问预案

**Q：小时级到分钟级，这个数怎么来的？**
→ **必须说清口径**：小时级是"人工搬运 + 两轮校对"的流程估算；分钟级是跑一遍的实测。**口径比数字重要。**

**🔴 Q：分析师为什么不直接填模板？**（最狠的一问）
→ 模板里有四十多个字段（股价、市值、目标价、牌照编号），让他手填一样会错；多类报告共用模板时字段位置还会变。让他填模板只是把校对成本从排版挪到分析师身上，**总量没降**，而且分析师的时间成本高得多。

## 句 2｜基于 OpenCode 智能体框架，设计 3 个可协作 Agent Skill

### 面试口语稿

> "我基于 OpenCode 的智能体框架做了三个能力，是**按职责边界切的，不是按代码模块切的**。
>
> 第一个是数据访问层——**所有对数据库的读写必须走它，另外两个能力一行数据库都不直接写**。第二个管模板资产，把一份样本报告变成'带占位符的模板 + 一份字段定义表'。第三个管单篇报告，读模板、读草稿、出成品，生成完要通过第一个能力去提交。
>
> 所以这里的'**可协作**'不是说三个东西一起用，而是它们之间有**有方向的调用关系**：一个统一的出口，两个调用方。好处是认证只做一次、权限规则只有一份、审计不会漏，也不会出现某个入口绕过校验。
>
> 每个能力我还写了明确的**写权限边界**——管模板的只能动模板，管报告的只能动这一篇的产物。"

### 知识点深挖

**Skill 机制**：一个目录 = 一个能力。目录里有能力说明文件，开头写**触发短语**（用户说什么话激活它），正文写工作流，附件放脚本和参考资料。核心特性是**渐进式披露**——正文保持短，重的东西放附件，**只有真用到才被读进上下文**。

**"可协作" = 有方向的调用关系，不是并列关系**：

```
   Template Maker ──┐
                    ├──→  Neolyst  ──→  数据库（唯一出口）
   Report Maker  ───┘
```

**"唯一出口"（单点收口）的四个好处**：

| 好处 | 具体是什么 |
|---|---|
| 认证只做一次 | 凭据管理只有一处，其他能力不需要知道数据库在哪 |
| 权限模型只有一份 | 不会出现"某个入口绕过了权限判断" |
| 错误处理统一 | 什么该重试、什么该抛给用户，只定义一遍 |
| 审计天然完整 | 所有写操作走同一出口，状态变更日志不会漏 |

**这是第二段的伏笔**——三层权限、状态机审计全部落在这一个出口后面。

### 为什么这么设计

两个理由：
1. **上下文预算**——模型能记住的有限，按需加载是按"什么时候需要"组织知识
2. **可独立评测 + 可被程序调用**——第三个能力要提交报告，完全不需要知道数据库地址和密钥，**只要调第一个能力的接口**

**反直觉的点**：拆开之后每个能力的说明**反而更容易写清楚**。"你有时是模板模式、有时是报告模式"是模型最容易犯迷糊的写法；拆成三个独立能力，边界就变成一句话。

**为什么是 3 个**：切的依据是**职责边界**，不是代码量。三类职责是"管资产 / 管单篇 / 管数据"，再拆就会出现两个能力改同一批文件，边界不干净。

### 追问预案

**🔴 Q：为什么用 OpenCode，不用 LangChain / LangGraph？**（必问）

分三层答：
1. **先说判断标准**：选编排方式看任务的 agent 特性。我这个场景是「**人机交互 + 工具调用 + 长流程状态**」，不是「多 agent 自主博弈」
2. **再说为什么合适**：它是**编码型 agent 的工作台**，原生支持能力机制和文件系统操作——而这个任务的重头戏恰好是读写 Word、管理文件产物
3. **主动给替代方案的适用场景**（关键）：
   > "**如果流程变成无人值守的批处理**——每天自动处理上百份草稿、不需要人确认——那我会改用图编排，因为那种场景要的是**显式的状态节点和可恢复的重试**。**选型差异的根源是'有没有人在环里'。**"

**Q：如果 agent 判断错了进哪个能力？**
→ 触发短语是语义判断，**不保证 100% 准**。所以关键操作不靠路由，靠**底层约束**——状态流转在数据库层拦，路由错了也越不过去。**路由负责体验，约束负责正确性。**

**Q：三个能力互相调用会不会死循环？**
→ 调用关系是**单向的**（两个调用方 → 一个出口），拓扑上无环。**这是刻意的设计。**

**⚠️ Q：写权限边界是提示词约束还是代码强制？**（软肋，主动说）
→ 现在是写在能力说明里的**提示词层面**约束。正确做法是给每个能力受限的文件作用域，或在写文件入口做路径白名单。**主动说出是加分，被问出来是减分。**

## 句 3｜以任务路由与工具调用编排全流程，支撑 9 类中英文报告自动生成

### 面试口语稿

> "编排上我做了**两层路由**，性质完全不同。
>
> **第一层是能力路由**——模型根据每个能力的触发短语决定进哪个环节，这是语义判断，灵活、零代码，但不保证百分之百准。**第二层是状态流转**——报告从草稿到提交、到发布、到退回，这一层不是模型说了算，是数据库层的硬约束，非法流转直接拒。
>
> 我这么分的依据是**后果的不可逆性**：路由错了用户立刻会发现，成本可恢复，所以可以交给模型图灵活；状态错了是合规事故，成本不可恢复，所以必须钉死在最底层。**路由负责体验，约束负责正确性。**
>
> 至于三个阶段——模板制作、内容生成、审核入库——**它们不是一条流水线，因为节奏完全不同**。模板是低频、长生命周期的**资产**；内容是高频、一次性的**产物**；审核是**人在环**，审批人拍板。三段生命周期差一个数量级，所以必须拆开。
>
> 覆盖面上，系统不认识'报告类型'这个具体值，它只认**字段定义表 + 模板**两个可替换件，报告类型只是查找键。所以加一类报告不是写代码，是走一遍制作流程。物理模板三套，通过显式的复用声明覆盖九个类型。"

### 知识点深挖

**两层路由的性质对比**：

| | 能力路由 | 状态流转 |
|---|---|---|
| 谁做决定 | 模型（语义判断） | 数据库（确定性约束） |
| 可靠性 | 不保证 100% | 100% |
| 错了的后果 | 可恢复（用户立刻发现） | **不可恢复（合规事故）** |

**核心原则：按后果的不可逆性分配可靠性。**

**三阶段节奏对比——为什么不能做成一条流水线**：

| | 模板制作 | 内容生成 | 审核入库 |
|---|---|---|---|
| 频率 | 极低 | 高（每篇一次） | 每篇一次，**人触发** |
| 产出性质 | **可复用资产** | **一次性产物** | **不可逆记录** |
| 生命周期 | 长（月到年） | 短 | 永久 |
| 谁拍板 | 模板维护者 | 分析师 | **审批人** |

> 硬做成一条流水线，就会被逼着**为最高频的阶段承担最低频阶段的开销**。

**"审核入库"四个字已经把「人在环」写进去了**——审核是人做的动作，入库是系统的动作。**模型可以帮人到"提交"，但到不了"发布"。**

**9 类报告 = 数据驱动，不是代码驱动**：系统只认「字段定义表 + 模板」两个可替换件。物理模板 3 套覆盖 9 类（宏观套被 4 类共用，快讯套被 3 类共用），**复用关系是显式声明、带校验的**：源模板必须已发布、语言必须一致、不能自己复用自己。口头约定在组织里活不过三个月。

### 追问预案

**Q：九种报告都要单独开发吗？**
→ 代码零改动 + 三套模板覆盖九类 + 复用是显式声明带校验的。

**Q：为什么模板制作和内容生成不合成一个流程？**
→ 生命周期差一个数量级（见上表）。**这是本句最能出彩的地方。**

**Q：审核环节能让 agent 自动通过吗？**
→ **不能，而且是刻意的。** 模型可以帮人到"提交"，发布权永远在人手里——研报要签字担责。**这不是能力限制，是责任设计。**

**🔴 Q：九类报告现在都能跑通吗？中英文都有吗？**
→ 见第三章口径审计。**必须改简历措辞。**

**Q：路由错了怎么办？**
→ 除了底层约束，还有一层：**路由错了会在字段表上留下信号**——报告类型选错，字段定义表就对不上草稿内容（该有的全空、不该有的全中）。**字段表本身就是路由正确性的检测器。**

## 句 4｜两阶段管线：LLM 依 Schema 抽取字段并定位内容块

### 面试口语稿

> "核心是**两阶段管线**。我先说它的对立面：还有一条路是端到端，让模型直接把草稿变成成品文档。我不用它是因为三个代价——**不可复现、不可回归测试、不可审计**，而研报要签字担责，这三条每条都是硬伤。
>
> 所以我切成两段：**第一段只做理解**，从草稿里读出结构化信息；**第二段只做执行**，纯确定性程序把结果落进模板。**两段之间是一份静态的、可读的、可审的理解结果——一组字段值加一组段落坐标。** 整个系统的可靠性就建立在这份接口可被检查上。
>
> 这里有一点我想强调：**'抽取字段'和'定位内容块'是两种性质不同的任务**。抽取是**生成性**的——草稿里没写，模型可能编一个看起来合理的数；定位是**判别性**的——它只能指向文档里真实存在的段落，**几乎没有幻觉空间**。所以我**按风险分配防护强度**：定位只做轻量合理性检查，字段才是重兵把守。
>
> 分工上我按**数据的结构化程度**分三层：**字段级是确定性规则优先**——表格里的键值对，规则比模型更准更快更便宜；**整篇级是模型定位、程序按范围切**——因为草稿是自由叙述的，没有结构可依；**执行层是纯确定性**，一个字都不赌。所以在我这里，**确定性在结构化场景下不是兜底，它本来就是更优解。**"

### 知识点深挖

**"两阶段"的价值在于它的对立面**——必须能说出「端到端」为什么不选：

| 端到端的代价 | 说明 |
|---|---|
| 不可复现 | 同一份草稿跑两次结果不一样 |
| 不可回归测试 | 改一处没法验证旧的还对不对 |
| 不可审计 | 成品里哪个字是模型写的说不清 |

**两段之间的接口**（判断是否真懂这段架构的试金石）：
> 一组**字段值** + 一组**段落坐标**，必须是**静态的、可读的、可审的**。

**本句最强的技术区分——抽取 vs 定位**：

| | 抽取字段 | 定位内容块 |
|---|---|---|
| 输出 | **一个值** | **一个坐标** |
| 性质 | **生成性** | **判别性** |
| 幻觉风险 | **有** | **几乎没有** |
| 兜底手段 | 人工确认 + 高风险断言 | 轻量合理性检查 |

> **按风险分配防护强度，而不是平均用力。**

**三层分工（按数据的结构化程度，务必按这个说）**：

| 层次 | 处理什么 | 谁来干 | 为什么 |
|---|---|---|---|
| **字段级** | 表格里的键值对 | **确定性规则优先** | 结构化数据规则比模型更准更快更便宜 |
| **整篇级** | 摘要/正文的**边界** | **模型定位**，程序按范围切 | 草稿无结构可依，只能靠理解 |
| **执行层** | 填模板、搬内容 | **纯确定性程序** | 排版正确性一个字都不能赌 |

> **核心判断标准**：不是「模型 vs 规则」，而是**按数据的结构化程度分工**。越是结构化的数据，越该交给规则；越是自由叙述的内容，规则无能为力，才交给模型。

**Schema 三层解释**：
1. **是什么**——字段清单，每个字段带语义说明、格式示例、类型
2. **谁写的**——**从真实样本报告反向提取**，不是手写，是模板制作环节的产物
3. **为什么是数据不是代码**——系统不认识"目标价"这个字段，只认识清单里有一条叫目标价。**加字段不改代码，改清单就行。**

**格式为什么用示例值而不是严格规则**：
- 示例值让模型**泛化**，看一个例子就懂意图
- 代价：**示例值对模型是软约束，不是硬校验**，可能返回带单位的"86.72 港元"
- 所以**没指望 schema 做最终校验**，校验放在确认和断言环节

### 为什么这么设计

因为**模型的输出不可复现、不可测试、不可审计**——同一份草稿跑两次，措辞可能不一样。而研报要签字担责。

> 设计原则：**把模型的输出压缩成可校验的结构化信息**——字段值（人能过目）+ 段落坐标（能指回原文）。凡是要求"必须完全一致"的部分，一律不交给模型。

### 追问预案

**Q：25+ 字段具体是哪些？**（高频，务必背下来）
→ 报分类，别报流水账：
- **分析师信息**——最多八位，每位四样：中文名、英文名、牌照编号、邮箱
- **公司信息**——中英文名、股票代码
- **行情数据**——当前价、市值、五十二周高低、价格日期
- **评级与目标价**
- **报告标题与日期**
- 加起来**五十多个字段**，其中四个是整段内容（摘要、正文、英文摘要、法律附录），另有**两个图表由系统自动生成**

**Q：Schema 谁写的？写死了以后加字段怎么办？**
→ 从样本报告反向提取，不是手写；加字段改清单不改代码。

**Q：模型抽出来的值稳定吗？**
→ **大部分字段是确定性规则抽的，本来就稳定**；只有规则覆盖不到的才交给模型。但**从工程角度我不假设模型输出稳定**——关键不是"保证它稳定"，是"**稳定不稳定都不影响最终交付**"，因为后面有确认环节。

**Q：草稿里没有这个字段呢？**
→ **留空，绝不猜**，并在确认表里**醒目标出来**。人看到空格就会去补，比模型猜一个值安全得多。

**🔴 Q（陷阱）：模型会不会把草稿里没有的内容编进字段？**
→ **必须承认会。** 三层应对：① 确定性规则优先，把大部分字段的风险前移消掉；② 确认表让人过目，空字段醒目标记；③ 高风险字段（评级、目标价、价格日期）加确定性断言——评级必须命中枚举、目标价必须在合理区间、日期必须能解析，**不满足就标红退回，而不是静默写进去**。**第 ③ 条还没做，但作为"下一步"说出来，比含糊过去强得多。**

**⚠️ 表述陷阱**：实现上字段抽取是「**确定性规则优先、模型补漏**」，且规则结果优先级更高（模型只填空值、不覆盖）。这和"LLM 理解 + 确定性兜底"听起来相反。
**它不矛盾，但你必须分层说**：字段级 = 规则优先 + 模型补漏；整篇级 = 模型定位 + 确定性切分；执行层 = 纯确定性。**三层混成一句说，被追问到细节时会当场对不上。**

## 句 5｜格式执行交由确定性代码兜底，将幻觉隔离在可校验的理解层

### 面试口语稿

> "'幻觉隔离'不是修辞，是**架构上限制了模型能编造什么**。正文部分模型根本没机会编——它只输出段落范围，真正往成品里塞内容的是确定性代码，按范围从原草稿**原样搬过去**。所以正文里的每一个字都是原文的切片，**物理上不可能出现幻觉**。
>
> 模型可能编的只有字段级：草稿里没写目标价，它可能推一个看起来合理的数。对这种我用两步收口：一是把抽出来的所有字段渲染成一张带标记的确认表，**空字段会被醒目标出来**，让人过一眼；二是高风险字段后面还要加确定性校验。"

### 知识点深挖

**业界对应说法**：**"定位而非生成"**（locate, don't generate）。

| | 检索增强（RAG） | 本方案 |
|---|---|---|
| 流程 | 找到原文 → **模型组织语言回答** | 模型只指路 → **原文原样落地** |
| 输出 | **仍是模型生成的** | **零生成** |
| 解决什么 | 知识过时 | **措辞漂移** |

**模板里的占位符是目标槽位，不是搜索键**：
> 不是"拿着占位符去草稿里搜内容"，而是"**先理解出内容在哪，再搬进对应的槽位**"。方向是**从草稿到模板**，不是从模板到草稿。

**"内容块"为什么要用另一种填充机制**：
- 字段是**一个值**，替换一个位置就行
- 内容块是**一整段内容**——摘要要填进封面右侧特定区域；正文可能二十多页，**必须原样保留段落结构、标题层级、表格和图片**。压成纯文本塞进去，格式全丢
- 所以内容块要的是**按范围整体搬运**，不是替换一个位置

### 为什么这么设计

因为研报的**责任主体是人**。分析师签字的报告，一个字都不能是机器编的。
> 目标不是"让 AI 写得像样"，而是"**让 AI 只做搬运工**"。

### 追问预案

**⚠️ Q：兜底是流程兜底还是技术兜底？**
→ **字段级的兜底靠人工确认，属于流程兜底。** 追问"半夜跑批没人确认呢"——诚实答：这套流程设计上就是**人机协作，没有无人兜底路径**。这么答不失分，反而说明你清楚系统边界。想加分就补：高风险字段加确定性断言，不满足就标红退回。

**Q：正文原样搬，那正文里的格式问题也一起搬进去了？**
→ 对，这是个真缺口。正文目前只做了缩进清理和字体统一，**没有做内容级校验**（标题层级是否连续、有没有孤立图片）。**主动说出来。**

## 句 6｜渲染后校验 + 人工确认形成闭环，单份报告由小时级降至分钟级

### 面试口语稿

> "验证这一步我在**成品上**做三件事。
>
> 第一，**法律披露附录必须存在**——这是合规红线，丢了就是事故，我直接扫文档底层结构确认它还在。第二，**字体约束**——中文统一楷体、英文统一 Calibri，在成品上强制覆盖，不受草稿字体五花八门的影响。第三，**分析师认证声明按人数展开**——模板里只有一份声明段落，实际有八个分析师就得有八份。
>
> 为什么要扫底层结构而不是用常见的文档库读段落？因为**那个库会漏读嵌在表格或复杂结构里的段落**，而附录恰好可能就长在表格里，只有直接遍历文档底层才不漏。"

### 知识点深挖

**普通文档处理库只暴露文档主体直接子级的段落**，而实际段落可以嵌在表格单元格、内容控件里，任意深度。法律附录这种"必须存在但位置不固定"的东西，**只能在最底层做全量扫描**。

> **任何时候需要"找遍全文"，都必须下沉到最底层。**

### 为什么这么设计

验证放在**渲染之后**而不是之前，因为要验的是**最终产物**。渲染前只能验输入对不对，渲染后能验"结构有没有被破坏"。**合规模板这种东西，结构完整性本身就是交付物的一部分。**

### 追问预案

**🔴 Q：渲染后自动校验具体验哪些？**
→ 见第三章。**这是整份简历唯一一处表述超出实现的地方，必须处理。**

**⚠️ Q：多分析师场景你验过吗？**
→ 现实是：多分析师认证声明的展开路径**实际不会触发**（判断分析师数量时用的字段名和字段定义表里的名字对不上）。**面试官看不到代码，但被追问"多分析师场景验过吗"时答"验过"有风险。建议修掉。**

**Q：分钟级里多少是模型调用、多少是渲染？**
→ 最好有实测拆分。没有就说"模型抽取是主要耗时项，渲染在秒级"，**别报没测过的数**。

## 句 1｜围绕全链路质量治理，自研文档解析与确定性渲染工具链

### 面试口语稿

> "第二段讲的是质量从哪来。我的出发点是：**质量不能靠末端检查拦住，要在每一段都设卡**。所以我把链路上的约束按五个位置铺开：输入侧解析草稿、转换侧切分内容、组装侧保住分节和页眉页脚、输出侧校验关键结构、流程侧约束状态和权限。**前四个是文档维度，第五个是流程维度。**
>
> 这条链路我是自研的，但我的取舍标准是：**优先用成熟库，只在库的能力边界之外才自己写**。读取侧，通用文档库拿不到深层嵌套的表格，而研报的财务表经常嵌套三层；组装侧，通用库合并文档会破坏分节结构，页眉页码会跟着乱。**但更根本的理由是责任——通用库给的是'能读写文档'，我要的是'保证研报的合规结构'，这个责任只能由我的代码承担。**
>
> 反过来说，**能用的地方我一律不自己写**：占位符替换、文档合并都用现成的。**我只在责任的边界上自研，不在能力的边界上自研。** 而且我敢自研的前提是这条链路**是确定性的**——同样的输入必然同样的输出，所以它**可以被测试**。我不自研不可测的东西；唯一不可测的那一步，我在第一段就已经隔离出去了。"

### 知识点深挖

**"全链路"是哪五段——要能报清单**：

```
① 输入侧   草稿解析——把自由格式文档读成可理解的结构
② 转换侧   内容切分——判定哪段是摘要、哪段是正文，按范围搬
③ 组装侧   模板渲染——合并内容与模板结构，保持分节/页眉/页脚/页码
④ 输出侧   成品校验——在最终产物上确认关键结构没丢
⑤ 流程侧   状态流转、权限、审计——报告的生命周期约束
```

**前四条是文档维度，第五条是流程维度。** 这就是为什么第二段后半能自然转到状态机，不是硬塞。

**"治理" vs "校验"**：
> 校验是末端动作，治理是每段都设卡。只靠最后检查一遍，检查成本随文档变长**线性上升**（二十页的成品只能通读）；分段设卡的成本是**固定的**。

**金句（直接背）**：**"质量不是检出来的，是设计出来的。"**

### 为什么这么设计

**"谁承担责任，谁就拥有代码"**——这是自研的判断标准，比"库做不到"更有分量。库做不到可以提 issue 等它修，但合规责任等不了。

**"确定性"是自研的准入条件**：
> 自研的风险是"自己写的东西没人保证它对"。我敢自研，是因为这条链路**是确定性的**——没有模型的随机性掺在里面，**所以可以被测试**。换句话说：**我不自研不可测的东西。**

### 追问预案

**Q：全链路具体是哪几条？**（最可能被问，务必背熟）
→ 五段清单。

**Q：为什么不用商业的研报排版产品？**
→ 商业产品定位是**通用模板引擎**，解决"文本替换成结构化文档"。它解决不了三件属于这个组织的事：**九类报告的复用关系**（业务规则不是排版规则）、**审批状态机**（流程不是文档）、**三层角色的数据权限**（组织不是格式）。**通用产品解决通用问题，解决不了组织问题。**

**Q：自研的东西怎么保证质量？**
→ **确定性和可测试性互为前提**。确定性让它可测，可测才允许自研。**不测的东西我不会自己写。**

**Q：维护成本考虑过吗？**
→ 自研的维护成本是真实的，所以**自研范围被严格限制在"责任边界内"**，通用能力一律外包给库。另外这层的接口**由输入产物定义**（字段清单 + 模板），业务变化不会穿透到代码层。

**Q（易被漏但关键）：你说质量治理，那出错了怎么发现？**
→ **分两类**。**静默失败**（结构坏了但文件能打开）靠**断言**拦——这是最危险的一类，必须在输出侧主动检查；**显式失败**（字段空着、定位不到）靠**确认表**让人看到。**别只说"校验"，要说清你在防的是"静默失败"。**

## 句 2｜深层嵌套突破 / 理解层上下文 / 渲染后校验

### 面试口语稿

> "这一句讲工程实现，三个点。
>
> **第一，深层嵌套表格。** 研报的财务表、股权结构表、估值表天生是表里套表的，常见两三层。通用文档库的读取接口是按主流场景抽象的，**给你的是最外层，里面套的拿不到**，结果就是核心字段全空。所以我跳过了封装，**直接遍历底层结构把所有表格都取出来**。这里的判断是：**封装换便利，代价是覆盖不全；业务正好长在边缘上时，就必须下沉一层。**
>
> **第二，理解层的上下文。** 这里我想强调：**模型输出的是坐标**——'摘要在第 3 段到第 7 段'。**这个坐标必须能落回原始结构，我才切得动。** 所以我从底层结构生成一份**带段落编号**的文本给模型，编号和原始结构一一对应，**理解层和渲染层共用一套坐标系**。这么设计还有个好处：**我把模型的'自由生成'降维成了'从有限集合里做选择'**——它不是在写内容，是在挑。而且编号这种输出简单到不会漂移，比让它输出结构化数据可靠得多。
>
> **第三，渲染后校验。** 为什么必须在渲染后？因为**渲染是多步合并，最典型的问题就是静默失败**——文件能打开，页眉没了。**交付环节才发现就晚了。**
>
> **⚠️ 这一块我要说清做到哪一步了**：现在已经落地的是**法律披露附录的存在性校验**——渲染完直接在成品上扫一遍底层结构，确认这段还在。这是合规红线，丢了就是事故，所以我先把它做了。
>
> **我原本要设的是三道卡**：附录存在性、**占位符残留**（客户看到文档里印着未替换的标记，这是灾难）、**分节结构**（分节一坏页眉页码就丢，交付时根本看不出来）。后两道**还在计划里，没落地**——这是我知道且明确要补的缺口，不是"我加了全面校验"。
>
> 至于断言设计，我守三条：**只断言结构和数量不断言内容、必须能报出具体位置、宁少勿滥**——一条老误报的断言最后会被人习惯性忽略，等于死了。"

### 知识点深挖

**① 深层嵌套是哪来的**：财务数据表（科目 × 年度）、股权结构表（合并单元格表达层级）、估值表（倍数 × 情景）——**业务本身就需要这个结构**，不是文档写得乱。

**② 本句最容易被讲浅的地方——为什么"解析"和"给模型看"要绑在一起**：

> 模型输出的是**坐标**，坐标必须能**落回原始结构**才能用来切内容。如果给模型看的是转出来的纯文本，而切的时候用的是另一套结构，两边"第 3 段"指的不是同一个东西——**坐标就失效了**。所以：**理解层和渲染层必须共用一套坐标系。**

**③ 升维的那一层（单独背下来）**：
> 把模型的"自由生成"降维成了"**从有限集合里做选择**"。它不是在写一段内容，是在**做挑选**。选择的可靠性和生成完全不是一个量级。而且编号是一个整数，**整数不会漂移**——比让模型输出结构化数据可靠得多（后者有漏字段、改字段名、层级套错的风险）。

**④ 断言设计三原则（本句最能体现成熟度的地方）**：

| 原则 | 说明 |
|---|---|
| 只断言**结构与数量**，不断言内容 | 内容对不对是前面环节的责任；**什么都断言等于什么都断言不了** |
| 必须能**定位到具体位置** | "第 12 段有残留占位符"才有价值；**可诊断性是一半的价值** |
| **宁少勿滥** | 一条老误报的断言，最后会被人习惯性忽略，等于死了 |

### 为什么这么设计

**"库的封装带来便利，代价是覆盖不全。抽象就会丢掉边缘情况。当你的业务正好长在那个边缘上时，就必须下沉到原始层。"**

但**下沉有代价**——要自己处理底层结构的所有细节。所以原则是：**能用封装就用封装，只在封装确实覆盖不到的地方下沉一层**，且下沉之后要立刻用测试固定住。

### 追问预案

**Q：你怎么知道库拿不到深层表格？**
→ 诚实答**是第一版失败发现的**："第一版跑完发现财务表的字段全空，排查才发现表根本没被读出来。"**从失败里发现的限制，比从文档里读到的限制更有说服力。**

**Q：直接操作底层结构，不怕格式版本差异吗？**（陷阱题，答好很加分）
→ "文档格式是**公开标准**，标签是稳定的；**真正不稳定的是库的 API**——库会改接口、会调整抽象。**所以下沉一层反而更稳定。** 代价是细节要自己管，所以这一层用测试固定住了。"

**Q：模型定位错了怎么发现？**
→ **坐标是可以被质疑的**：程序拿到坐标后检查"指的位置合不合理"（正文开头应该像标题而不是表格），不合理就退回重定位。再兜一层是人工确认。**诚实说：现在没有自动化的定位准确率指标。**

**Q：为什么不给那个库提改进，而要自己绕开？**
→ **那是库的设计取舍，它有它的道理**（简洁 API 对绝大多数用户是对的）。**我不需要改它，我只需要在自己这层下沉。** 不抱怨工具，各取所需。

## 句 3｜状态机固化于数据库层，非法流转拒绝 + 自动审计

### 面试口语稿

> "报告的生命周期我用**状态机**来管，而且我把状态机**固化在数据库层**，不是写在应用层。
>
> 我的判断标准是：**不变量应该放在它无法被绕过的地方**。应用层校验是**建议**，数据库约束是**规则**——应用层可以被绕过，换个客户端、写个脚本、以后新加的入口忘了加校验，**只要有一个入口绕过去，这个约束就不成立了**。放在数据库层，所有入口共享同一个校验。我一般说：**应用层校验像靠自觉，数据库约束像靠制度，制度绕不过去。**
>
> 状态有四个：草稿、已提交、已发布、已退回，**五条合法路径，其余一律非法**——是**默认拒绝**，不是默认允许。几条设计理由：**'已提交'是冻结态**，提交后不能再改内容，否则会出现'审批人批的是 A 版、发出去的是 B 版'；**'已退回'必须先回草稿**，改过了就是新版本，要重走一遍流程，堵住'一个字没改再交一次碰运气'；**'已发布'是终态**，因为对外承诺不可撤回。
>
> 拦截是**写在写入之前**的——写完再回滚意味着非法状态曾经短暂存在过。至于权限，**状态机只管'能不能转'，'谁能转'是权限层的事**。
>
> 审计是**自动**的：状态一变，日志必然产生，**两者是同一次写入的两个结果**。这么做的价值不是省事，是**不可能漏**——靠应用层记得写，总有一天会漏，而审计链条漏一条就全废了。日志只允许追加，**修改和删除权限根本没给任何角色**。"

### 知识点深挖

**状态机图（要能当场画出来）**：

```
draft ──提交──→ submitted ──发布──→ published
  ↑                 │
  └──撤回───────────┤
                    ↓ 退回
                 rejected
                    │
  └──撤回───────────┘
```

| 路径 | 谁做 | 为什么存在 |
|---|---|---|
| 草稿 → 已提交 | 分析师 | 提交审批 |
| 已提交 → 已发布 | 审批人 | 通过 |
| 已提交 → 已退回 | 审批人 | 打回，**必须写理由** |
| 已提交 → 草稿 | 分析师 | 撤回修改 |
| 已退回 → 草稿 | 分析师 | 重新开始改 |

**四条设计理由（一条都不能少）**：

1. **"已提交"是冻结态**——否则会出现"审批人批的是 A 版、发出去的是 B 版"，**审批形同虚设**
2. **"已退回"不能直接回"已提交"**——必须重回草稿。改过就是新版本，**让路径变长一点点，就堵住了"一个字没改再交一次碰运气"**
3. **"已发布"是终态**——**对外承诺不可撤回**。系统里改回草稿，客户手里那份不会变，**系统状态和现实就不一致了**。要改只能停用旧的、发新的。**这是合规思维，不是技术限制**
4. **状态机管"能不能转"，权限管"谁能转"**——两个关注点分开，各自能单独改、单独测

**"默认拒绝"**：任何没列出的路径都非法。

**为什么"直接拒绝"的"直接"很重要**：
> 写在**写入之前**拦，不是写完再回滚。区别：写完再回滚意味着数据里**曾经短暂存在过非法状态**（同一时刻别的查询可能读到）；而且回滚是异常路径，副作用和日志难处理。

### 追问预案

**Q：为什么不自己搭后端，要用 Supabase？**
→ 三类后端能力开箱即用：**认证、数据接口、文件存储**，还有**数据库层的权限模型**。**取舍**：省掉大量基础设施代码，代价是业务逻辑要往数据库推、可移植性打折。所以下推范围**严格限制在状态流转和权限**这两类"必须无法被绕过"的规则上。

**Q：数据库里的逻辑，调试不难受吗？**
→ **诚实承认是真实代价**：错误信息不如应用层直观、逻辑和业务代码分家。**缓解**：错误信息写清楚（带上 from/to）+ **用测试把每条合法路径和每条非法路径都固定住**。

**Q：审计日志会不会越来越臃肿？**
→ 量级极小：**只在状态变化时写**，一篇报告最多几次。**这是刻意收窄的**——连字段修改都记的话，大量噪音会淹掉真正重要的状态流转。

**🔴 Q：审计能被伪造或篡改吗？**（软肋）
→ **追加不可改、删除不可做，这两点是真的**；但**写入路径没有强制绑定操作人身份**——理论上有权限的角色可以手工插一条流转记录。**诚实说出来**，方向：把审计写入收进受控的存储过程，强制操作人取当前登录身份。

**Q：用 BaaS 不怕被厂商锁定吗？**
→ **状态机逻辑和权限规则都是标准 SQL**，换平台要重写的是接入层，不是规则本身。**真正被锁定的是"用它的方式思考"**，所以业务逻辑尽量留在应用层。

**Q：状态机会不会限制业务灵活度？**
→ 反过来想：**状态机是一张所有人都能看的清单**。没有状态机的时候，规则散在代码里，改一条要读十个地方——**那才是真的不灵活**。

## 句 4｜3 层 RLS 行级权限隔离数据，模板运行时动态解析

### 面试口语稿

> "权限是三层角色：管理员、审批人、分析师。规则是：管理员看全部；审批人只看已提交、已发布、已退回的报告和日志；分析师只看自己拥有的加所有已发布的。**'已发布'是用一条独立规则实现的**——同一个角色两种可见条件，写成一条会让规则变得难读也难维护。
>
> 更新权限更严：分析师只能改自己的草稿，审阅中和已退回都不能改。
>
> 模板这块是运行时向数据库要的——按'报告类型 + 语言'查出该用哪套模板再去取。**模板不打包在代码里，改模板不用发版。**"

### 知识点深挖

**RLS 是"行级"的，不是"列级"的**——追问"能不能隐藏某个字段"，答：RLS 做不到，需要建视图或列权限。**这是个真实的知识边界。**

**角色从登录令牌的声明里取，不是每次去查用户表**——避免每次权限判断都打一次数据库。追问"角色能自己改吗"：该声明只有服务端权限能写，用户改不了自己的令牌。

**"3 层"的准确含义是 3 个角色，不是 3 条策略。别被问住。**

**"模板运行时解析"的含义**（详见第四章）：

| | 写死 | **运行时解析** |
|---|---|---|
| 模板放哪 | 跟代码打包 / 路径写死 | 独立资产，存在数据库/存储里 |
| 怎么找 | 代码直接指向文件 | **拿"报告类型 + 语言"去查** |
| 改模板 | **重新发版部署** | **下一篇报告自动用新的** |
| 谁能改 | 只有能发代码的人 | 有模板权限的业务人员 |

### 为什么这么设计

**纵深防御**：能力层做业务校验 → 数据层做状态约束 → 权限层做可见性。**任何一层被绕过，其他两层还在。**

**为什么叫"解析"而不是"加载"**：因为**查找键和模板不是一对一**——"量化报告 + 中文"可能指向"复用宏观那份"，取值时要跟着这条声明走到真正的模板。**中间有一次映射，所以是解析。**

### 追问预案

**Q：模板缓存在哪？更新了怎么通知？**
→ **没做缓存就直说**："每次取一次，量级不大可以接受。"**别编缓存机制。**

**Q：为什么不把模板打包进应用，用配置切换？**
→ 配置切换仍然要**发版**才生效——**配置文件和代码是同生共死的**。而且配置文件没法表达"复用关系"，也没法做权限和审计。

**Q：模板更新了，已经在流程中（已提交待审批）的报告怎么办？**
→ 报告一旦生成就是**静态产物**，模板更新不影响已生成的。**如果没做过这个场景的验证，就说"没有特意处理，因为生成是一次性动作"。**

**⚠️ Q：运行时解析有什么代价？**
→ 四条，**主动说**：① 每次运行多一次网络往返和认证；② 有缓存就有新鲜度问题；③ **用旧模板生成的报告无法精确重放**——严格可追溯要记录模板版本号；④ **复用关系是静态复制**，主模板更新后复用方不自动同步，要重新执行声明。**前两条是设计必然代价，后两条是"知道但还没做"。**

## 句 5｜配套 30+ 自动化测试与评估用例，沉淀可复用组件，规模化落地

### 面试口语稿

> "最后是测试和沉淀。测试这条我分两类：**三十多个自动化测试，测的是确定性链路**——读取、切分、组装、修复、格式，还有状态机的每一条合法路径和**非法路径**。模型那一层不在这里，是设计使然：**第一段把模型隔离出去，直接效果就是渲染链路上绝大部分代码是可单测的**。我敢自研这条链路，就是因为它**确定性、可测**——**不可测的东西我不会自己写。**
>
> 另一类是**能力层的评估用例**，测的是模型行为是否符合预期。这一类现在是人工看，**下一步要把它结构化才能自动判分**。
>
> 沉淀的可复用组件是四类：**字段定义表**（数据契约）、**模板和复用声明**（资产复用）、**能力说明文件**（能力契约），还有**工具链本身**。复用发生在两个层面——同一类报告内部的字段共享，和跨报告类型的模板复用。
>
> 至于规模化，我指的是**报告类型的规模化，不是请求量的规模化**。判断标准是**新增一类报告的成本结构变了**：原来是写代码，现在是放样本、生成模板和字段表、发布，**代码零改动**。**但我要说明：我没做过并发压测**，能同时跑多少篇这个问题我答不了。"

### 知识点深挖

**"30+"的核对**：项目里测试文件是 **34 个**，覆盖三个能力。**数字是准确的。**

**测试的边界必须说清**：
> **测的全是确定性链路——模型那一层不在这三十多个里。** 这不是遗漏，是设计使然：把模型隔离在理解层，直接效果就是**渲染链路上绝大部分代码是可单测的**。

**测试覆盖的六类**：

| 环节 | 测什么 |
|---|---|
| 读取 | 嵌套表格能否被完整读出（**正是当初踩坑处，现在有测试守着**） |
| 切分 | 按范围提取是否精确 + 边界情况（只有摘要没正文等） |
| 组装 | 合并后分节、页眉页脚是否还在 |
| 修复 | 被 Word 拆散的模板标记能否正确还原 |
| 格式 | 字体约束是否覆盖所有文本 |
| **流程** | 状态机**每条合法路径 + 每条非法路径** |

> 状态机的价值在于"非法路径被拒绝"，**所以非法路径必须有测试**——不然你只是"相信"它被拒绝了。

**单元测试 vs 评估用例**：

| | 单元测试 | 评估用例 |
|---|---|---|
| 测什么 | **函数对不对**（确定性断言） | **能力表现对不对**（行为符合预期） |
| 为什么需要 | 代码会改，要防回归 | **模型输出是概率性的**，没法断言精确值 |
| 怎么判断 | 断言通过/失败 | 观察行为是否符合期望描述 |

**可复用组件四类**：

| 类别 | 是什么 | 复用在哪 |
|---|---|---|
| **字段定义表** | 一类报告的**数据契约** | 加字段、加报告类型都不改代码 |
| **模板 + 复用声明** | **资产层复用**：3 套模板覆盖 9 类 | 新类型可声明复用 |
| **能力说明文件** | **能力契约**：触发条件、工作流、写权限边界 | 新能力照此结构加 |
| **工具链本身** | 解析/切分/组装/校验 | 后续所有报告类型共用 |

**复用发生在两个层面**（要能区分）：
1. **同一类报告内部的字段复用**——分析师信息、评级、行情，每篇公司报告都要
2. **跨报告类型的模板复用**——9 类只有 3 套物理模板

**"规模化"的正确定义**：
> 指的是**报告类型的规模化，不是请求量的规模化**。判断标准是**新增一类报告的成本结构变了**。

**规模化的三个前提**（有深度）：

| 前提 | 对应哪一句 |
|---|---|
| **确定性**——链路可测，才敢批量跑 | 句 1、2 |
| **资产化**——模板和字段表独立演进 | 句 4 |
| **流程固化**——状态机和权限在数据库，人不用记流程 | 句 3 |

### 追问预案

**Q：三十多个测试都测什么？** → 按六类报，**特别强调非法路径也有测试**。

**Q：有 CI 吗？** → **没有就直说**。加一句"本地跑，接 CI 是下一步"就够了。
> **CI = 每次提交代码，服务器自动跑测试，坏了立刻报警。**把"该跑的检查"从"靠自觉"变成"靠流程"——和句 3 的"制度 vs 自觉"是同一个思路。
> **"写了测试但没接 CI"是工程节奏问题；"没写测试"才是能力问题。**

**Q：测试覆盖率多少？** → **没测过就别报数字。** 说"核心链路的正常路径和主要边界都有覆盖"，**不要说百分比**。

**Q：评估用例怎么判分？**
→ 现在**人工看行为是否符合预期**。要自动判分，得先把期望输出结构化——比如断言"提取结果里股票代码这一项应该等于某个值"，而不是写一句"应该正确识别股票代码"。**这一步还没做。**

**Q：能同时处理多少篇报告？**
→ **说没压测过，别猜数字。** 设计上每篇处理是无状态的，理论可并行；瓶颈会在模型调用和文件解析上。

| 5 | ⚠️ | 抽取 **25+ 字段**，实际**五十多个** | 数字保守可接受，**但被问时要能当场报出分类** |
| 6 | ⚠️ | 字段级实现是"**规则优先、模型补漏**"，与对外表述方向看似相反 | **必须按三层说清**（见第一段句 4） |
| 7 | ⚠️ | "自动**快照**"措辞 | 记为"变更那一刻整行关键字段的值"，不是字段级 diff。**改成"自动记录审计日志"** |
| 8 | ⚠️ | 写权限边界是**提示词约束**，非代码强制 | 主动说成改进项 |
| 9 | ⚠️ | 多分析师认证展开路径**实际不触发**（字段名对不上） | 修掉，或准备口径 |
| 10 | ⚠️ | 审计日志**未强制绑定操作人身份** | 主动承认 + 给方向 |
| 11 | ⚠️ | "规模化"易被理解成吞吐量 | 提前定义为"**报告类型的规模化**"，并主动说没压测 |

# 第四章 · 单点深挖问答

## 4.1 为什么不直接用 agent 把草稿填进 Word？是做不到吗？

**先纠正前提**：**不是做不到，是"能填"和"敢交"是两件事。** 而且**现在的系统里就是 agent 在填**——它决定填什么、填到哪一段，只是不决定怎么落进 Word。

**先把"填"拆开**：

| | 干什么 | 难度 | 谁擅长 |
|---|---|---|---|
| **定位** | 摘要在哪？正文从哪开始？ | **难**（草稿无结构约定） | 模型 |
| **执行** | 把第 3～7 段原样搬过去 | **简单**（机械搬运） | 确定性程序 |

**如果真让 agent 直接产出 Word，会坏在四个地方**：

| # | 问题 | 说明 |
|---|---|---|
| ① | **不可复现** | 同一份草稿跑两次结果不一样，**没法回归测试** |
| ② | **静默损坏结构** | 插错层级不会报错，而是**文件照常打开、只是页眉没了、页码从中间重来**。这种错不会被"打开看一眼"发现 |
| ③ | **长文档丢内容且贵** | 让模型逐字重新输出二十页正文，它会**无意识改写、压缩、漏段**（它在复述不是复制）；而程序搬一份结构是毫秒级零损失 |
| ④ | **审不了** | agent 直接填文档 → 只能**通读成品**确认；产出**结构化中间结果** → 人只审一张几十行的字段表。**审核面从"整篇报告"压缩到"一张表"**，这才是真正省下的东西 |

**还有个容易忽略的点——错误会累积**：
> 让 agent 一步步调工具插入，每一步都是出错机会，后面的步骤建立在前面的错误上，最后定位不到哪步坏的。**一次性产出完整的提取结果，错误就被收敛到一个点上**——静态、可检查。

**什么时候"agent 直接填"才是对的**：
> 一锤子买卖、短文档、没有审批流、没人签字、格式要求不严——**那让 agent 直接改文档完全没问题，反而开发更快**。这里约束完全相反：要签字、有合规要求、要跑成百上千篇、模板还会改版。**约束决定架构，不是架构决定约束。**

**30 秒口语稿**：
> "能填，现在就是 agent 在填——它决定填什么、填到哪一段，但不负责落进文档结构。原因是**搬运这件事程序做得比模型更好**：更快、更便宜、完全可复现。模型的价值在理解，不在搬运。而且**文档结构被破坏是静默的**——文件照样能打开，只是页眉没了。这种错不能在交付环节才发现。"

**MCP 有现成的 Word 工具，不就解决了？**
→ 那些工具**正是"模型给指令、工具去执行"**，和我这个设计是同一个思路。区别在**交互步数**：多轮调用逐段插入，错误一步步累积，中间状态没法审核；一次性产出提取结果，中间结果静态、可审、可复现。**工具化适合轻量编辑，不适合有合规要求的长文档批产。**

## 4.2 "模板运行时解析"指什么？

**一句话**：代码里不存模板，也不存"这份报告用哪个模板"。代码只有一个查找键——**报告类型 + 语言**。真正用哪份，是每次运行去数据库查出来的。

**三个收益（按重要性）**：

1. **改模板不用发版**——模板的变更频率比代码高一个量级，绑在一起会逼着代码跟着变
2. **模板和字段定义表成对发布**——从机制上杜绝两边不一致
3. **复用关系可以被显式声明**——九类只有三套物理模板，声明带校验（源必须已发布、语言一致、不能自复用）

**为什么叫"解析"而不是"加载"**：因为**查找键和模板不是一对一**——"量化报告 + 中文"可能指向"复用宏观那份"，要跟着声明走到真正的模板。**中间有一次映射。**

**40 秒口语稿**：
> "意思是**模板不在代码里**。代码只有一个查找键——报告类型加语言，运行时查出该用哪份模板。好处是**改模板不用发版**，而且模板和字段定义表成对发布。至于为什么叫解析——因为**查找键和模板不是一对一**，量化报告声明的可能是'复用宏观那份'，中间有一次映射。
>
> 代价我也清楚：多一次网络往返要缓存，缓存就有新鲜度问题；模板更新后旧的报告用哪一版说不清——**严格的可追溯要记录模板版本号，这一条我还没做**。"

---

## 4.3 "30+ 自动化测试与评估用例"是什么意思？

见第二章句 5，以及第三章第 2 处口径修改。

**最需要记住的一句**：两个是**不同性质**的东西——单元测试测**确定性代码**，评估用例测**概率性能力**。**在简历里并列写数字会让人误以为评估用例也有 30 多条。**

## 4.4 CI 是什么？

**CI = Continuous Integration（持续集成）**

每次提交代码，服务器**自动**跑一遍测试和检查，坏了立刻报警——而不是等你自己记得在本地跑。

| | 没有 CI | 有 CI |
|---|---|---|
| 流程 | 改代码 → 自己记得跑测试 → 提交 | 提交 → **自动**跑测试 + 检查 → 通过才允许合并 |

**它解决的问题**：人总会忘、也总有人偷懒。**把"该跑的检查"从"靠自觉"变成"靠流程"**——和句 3 的"制度 vs 自觉"是同一个思路。

最常用的是 GitHub 自带的 GitHub Actions。

# 第五章 · 高频追问速查（面试前 1 小时看）

## 一页纸

**开场就要主动说的三件事**：
1. **agent 决定填什么，但落盘由确定性代码做**——模型的价值在理解，不在搬运
2. **路由负责体验，约束负责正确性**——按后果的不可逆性分配可靠性
3. **质量不是检出来的，是设计出来的**——每段设卡，不是末端检查

**必须能当场报出来的数字**：

| 数字 | 值 |
|---|---|
| Agent Skill 数量 | 3 个 |
| 报告类型 | 9 类 |
| 物理模板 | 3 套（覆盖 9 类） |
| 公司报告字段 | 50+ 个（简历写 25+ 是保守） |
| 状态数 / 合法路径 | 4 个 / 5 条 |
| 权限角色 | 3 个（管理员/审批人/分析师） |
| 测试文件 | 34 个 |
| 评估用例 | **3 条**（薄弱点，别夸大） |

**四句能救命的金句**：
- "**应用层校验像靠自觉，数据库约束像靠制度。**"
- "**封装换便利，代价是覆盖不全；业务长在边缘上时，必须下沉一层。**"
- "**我把模型的自由生成降维成了从有限集合里做选择。**"
- "**质量不是检出来的，是设计出来的。**"

**遇到答不上来的，用这三句**：
- "**这个地方我没有实测数据，不能给你数字。**"
- "**这是我明确的下一步，现在还没做。**"
- "**我知道这是个缺口——现在是这样绕过的，正确的做法应该是……**"

**绝对不要做的事**：
- ❌ 编数字（耗时拆分、覆盖率、并发量）
- ❌ 声称做过没做的事
- ❌ 把三层的"LLM 优先/规则优先"混成一句话说
- ❌ 说"我给每个环节都加了校验"（应该按风险分配）

# template_maker 设计文档

**日期**: 2026-03-24
**状态**: 设计中
**版本**: 1.0

---

## 1. 概述

### 1.1 目标

`template_maker` 是分析师报告自动化系统的核心技能之一，负责：
- 从标准 Word 样本创建可复用的报告模板
- 通过自然语言维护模板和提取规则
- 管理报告类型到模板的路由映射

### 1.2 设计原则

- **业务友好**：YAML 格式简洁，业务人员可读
- **对话式交互**：零学习成本，通过自然语言完成所有操作
- **职责单一**：只负责模板资产，不处理单篇报告

---

## 2. 核心功能与边界

### 2.1 职责（做什么）

| 功能 | 描述 |
|------|------|
| 创建新模板 | 解析 Word 样本 + elements.yaml，生成模板资产 |
| 维护模板 | 通过对话添加/删除字段，同步更新 schema 和模板 |
| 管理路由 | 维护 router.yaml（报告类型 → 模板名映射） |
| 验证模板 | 执行最小渲染测试，确保模板可用 |

### 2.2 边界（不做什么）

- 不处理单篇报告（不写入 `/reports/`）
- 不直接修改已存在的报告目录
- 不负责最终的报告渲染（由 `report_maker` 负责）

## 4. 核心数据结构

### 4.1 schema.yaml（提取规则）

**扁平化设计，所有字段和片段在同一层级：**

```yaml
# schema.yaml

# === 普通字段（从样本文档提取，用于填充模板）===
report_date:
  description: 报告日期
  format: "21 Oct 2025"

company:
  description: 公司名称
  format: "西锐飞机"

ticker:
  description: 股票代码
  format: "700.HK"

title:
  description: 报告标题

rating:
  description: 评级
  format: "优于大市"

target_price:
  description: 目标价
  format: "11.12美元（对应港币86.72元）"

current_price:
  description: 现价
  format: "340.80"

market_cap:
  description: 市值
  format: "10000亿港元"

# === Word 片段（从原始文档摘取，保存为独立 Word 文件）===
abstract:
  type: fragment
  description: 报告摘要部分
  scope: 首页右侧（长的话可能到第二页），摘要后面有换页符
  hints:
    - 通常包含投资亮点、核心观点
    - 长度约 200-500 字
    - 位于首页右侧区域
    - **摘要后面一定有换页符**（在 Word 中体现为分节）

body:
  type: fragment
  description: 报告正文部分
  scope: 从第一个换页符之后到附录之前，正文结束后也有换页符
  hints:
    - 包含各章节详细内容
    - 可能包含表格、图表引用
    - 按原文结构保留段落和标题层级
    - **如果有正文，至少一页，正文结束后也有换页符**
    - **附录（信息披露）一定从新的一页开始**
```

**字段说明：**
- **普通字段**（无 `type`）：从样本文档提取的字段值，在生成报告时填充到模板中
- **Word 片段**（`type: fragment`）：从原始文档摘取的 Word 片段文件
  - `abstract`（摘要）是必须的，所有报告类型都有
  - `body`（正文）是可选的，例如 flash 报告通常没有正文
  - `scope`: 描述该部分在文档中的位置
  - `hints`: 提取时的提示信息

**设计原则：**
- 扁平化结构，所有内容在同一层级
- 通过 `type` 区分普通字段和 Word 片段
- 不需要 `format` 的字段可以省略
- 不包含必填校验（`required`），这是运行时逻辑
- 不包含版本信息，由 git 管理

## 6. 技术实现要点

### 6.1 核心依赖

| 库 | 用途 |
|----|------|
| `python-docx` | Word 文档结构解析 |
| `python-docx-template` | Jinja2 模板占位符处理 |

### 6.2 架构模式：混合模式（提示词 + 代码）

采用混合模式，平衡灵活性与可靠性：

#### 🧠 提示词负责（灵活部分）

| 功能 | 原因 |
|------|------|
| **解析 Word 文档结构** | 识别表格、段落、关键区域，LLM 理解能力更强 |
| **生成 schema.yaml** | 分析 elements.yaml 和 Word 样本，推断字段定义 |
| **识别动态内容** | 判断哪些是固定内容，哪些应该是占位符 |
| **修改模板** | "添加风险提示字段"这类自然语言指令，提示词更自然 |
| **生成变更预览** | 展示 diff，让用户确认 |

#### 🔧 代码负责（可靠部分）

| 功能 | 原因 |
|------|------|
| **文件 I/O** | 读写 `.docx`、`.yaml` 文件，需要 python-docx |
| **router.yaml 合并** | 避免误删除其他路由，需要结构化合并 |
| **Jinja2 占位符替换** | 精确替换文档内容，代码更可靠 |
| **确认与执行** | 用户确认后才应用，避免幻觉导致误操作 |
| **模板验证测试** | 需要实际渲染模板，不能只靠提示词 |

#### 架构流程

```
用户对话
    ↓
Orchestrator (core.py) ← Python 代码控制流程
    ↓
┌──────────┬──────────┬──────────┐
│ 提示词   │ 提示词   │ 提示词   │
│ 分析器   │ 生成器   │ 修改器   │
│ (分析结构)│ (生成schema)│ (变更预览) │
└──────────┴──────────┴──────────┘
    ↓
Python 执行层（读写、替换、验证）
```

### 6.3 Word 处理流程

```
Word 样本
    ↓
python-docx 解析结构
    ↓
提示词：分析文档结构、识别动态内容、生成 schema
    ↓
代码：替换占位符、生成 template.docx、更新 router.yaml
    ↓
验证测试（可选）
```

### 6.4 基于分节边界的自动检测

**关键结构特征（必须遵守）：**

分析师报告文档具有以下固定的结构特征：

1. **摘要后面一定有换页符**
   - 首页摘要区域结束后有分页（在 Word 中体现为分节）
   - 摘要通常在首页的表格中，右侧区域
   - 这是所有报告的通用特征

2. **正文至少一页，也有换页符**
   - 如果有正文部分，正文结束后也有分页（分节）
   - Flash 报告等简短报告可能没有正文部分

3. **附录从新的一页开始**
   - 信息披露、免责声明等附录内容在新页面（新分节）
   - 这是所有报告的通用特征

**技术实现（使用分节边界）：**
Word 文档使用**分节（Sections）**来实现不同的页面布局，而不是简单的换页符。分节边界是段落属性中包含 `sectPr` 的段落。

**自动检测策略：**

1. **分节边界检测**：
   - 扫描所有段落的 `pPr` 元素，查找 `sectPr` 属性
   - 返回包含 `sectPr` 的段落索引列表
   - 这些段落标记了各个分节的结束位置

2. **摘要位置检测**：
   - 扫描第一个表格中的单元格
   - 识别跨多列的、较长的文本（通常 >50 字符）
   - 优先检测合并单元格或右侧区域
   - 摘要通常位于首页的表格中

3. **正文范围检测**：
   - 分节 0: 标题/封面
   - 分节 1: 首页（包含摘要）
   - 分节 2: 正文内容（从这里开始）
   - 分节 3及以后: 附录（信息披露、免责声明等）
   - 正文从第三分节（索引 2）开始
   - 结束位置通过扫描最后一个分节中的附录关键词确定
   - 保留章节标题（以数字开头的短文本）
   - 保留已包含字段占位符的段落

4. **实现位置**：
   - `TemplateConverter._detect_section_boundaries()`：检测所有分节边界
   - `TemplateConverter._get_section_paragraphs()`：获取各分节的段落范围
   - `TemplateConverter._auto_detect_abstract_location()`：自动检测摘要位置
   - `TemplateConverter._auto_detect_body_range()`：自动检测正文范围

**手动配置与自动检测：**
- 用户可以手动指定 `abstract_range` 和 `body_range`
- 当未手动指定时，启用自动检测（默认行为）
- 通过 `--no-auto-detect` 禁用自动检测

## 9. 附录：设计决策记录

### 9.1 为什么 schema 这么简单？

**决策**：只保留 `name`、`description`、`format` 三个属性

**理由**：
1. **不包含 `required`**：提取规则应该只关注"提取什么"，校验是运行时逻辑
2. **不包含版本信息**：git 已有版本管理
3. **不包含 `type`**：第一版不需要强类型，后期可扩展
4. **`format` 独立**：结构化清晰，比嵌入 description 更易理解和维护

### 9.2 为什么选择对话式交互？

**决策**：`/template_maker` 触发，所有参数通过对话询问

**理由**：
1. 零学习成本，业务人员无需记忆命令参数
2. 自然语言引导，按需填写
3. 符合"业务人员自主配置"的目标

### 9.3 为什么使用 python-docx + python-docx-template？

**决策**：职责分离，两个库配合使用

**理由**：
1. `python-docx` 负责文档结构解析（识别表格、段落）
2. `python-docx-template` 负责模板占位符（基于 Jinja2）
3. 与 `report_maker` 技术栈保持一致
4. 成熟稳定，文档完善

### 9.4 为什么采用混合模式（提示词 + 代码）？

**决策**：分析和生成用提示词，执行和验证用代码

**理由：**
1. **灵活性与可靠性的平衡**：LLM 擅长理解和生成，代码擅长精确执行
2. **维护成本低**：通过提示词调整逻辑，无需改代码
3. **降低误操作风险**：用户确认中间结果后再执行
4. **可测试性**：代码层的测试更容易自动化

### 9.5 为什么 MVP 包含最小验证测试？

**决策**：第一阶段就用 elements.yaml 做一次渲染测试

**理由：**
1. **尽早发现问题**：模板结构问题在 MVP 阶段就能发现
2. **成本低**：用现有数据做一次简单渲染
3. **建立信心**：用户看到"验证通过"，增强信任感

### 9.6 为什么约定优于配置（elements.yaml 自动检测）？

**决策**：自动检测配对的 elements.yaml 文件

**理由：**
1. **减少输入**：文件通常成对出现，自动检测更方便
2. **约定清晰**：`<文件名> elements.yaml` 或目录下的 `elements.yaml`
3. **灵活兜底**：找不到时仍可显式指定

### 9.7 对话框文件上传如何处理？

**决策**：自动识别上传的 .docx 和 elements.yaml 文件对

**匹配规则：**
- `sample.docx` + `sample elements.yaml` → 自动匹配
- `sample.docx` + `elements.yaml` → 自动匹配（兜底）
- 只上传一个文件时，询问另一个

### 9.8 为什么要在对话中强调文档结构特征？

**决策**：在与用户的对话中明确告知以下结构特征：
- 摘要后面一定有换页符
- 如果有正文，至少一页，正文结束后也有换页符
- 附录（信息披露）一定从新的一页开始

**理由：**
1. **建立正确的心理模型**：帮助用户理解分析师报告的标准格式
2. **避免歧义**：确保用户理解"换页符"指的是分节（Section），而不是简单的分页符
3. **提高模板质量**：用户了解结构特征后，能提供更准确的配置信息
4. **降低沟通成本**：明确的结构特征减少了来回确认的需求
5. **支持自动检测**：系统基于这些特征实现自动检测，用户了解原理后更信任检测结果

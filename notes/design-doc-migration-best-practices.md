# 设计文档搬运判定规则

从设计文档向代码、README 和全局文档搬运内容时的判定原则。

## 总原则

- 任何具体问题，只要 Claude Code 可以通过查看代码、代码注释和数据库对象（含 SQL comment）准确回答，就不需要进文档，可以从设计文档中直接删除。

## 整理工作流

整理文档分四步，严格按顺序执行：

1. **识别整体流程**：通读整节，识别描述端到端流程的内容（如 save → validate → submit → 失败回 save），标记为整体单元，不允许拆散。
2. **拆命题**：把其余内容拆成一条条独立的命题（原子陈述），不丢信息。
3. **整理表达**：逐条把命题表达整理通顺，去掉冗余修辞，保留完整语义。
4. **去重分类**：核对命题之间是否有重复或重叠，按归属分配到小节。

**拆命题的粒度**：每条命题只含一个断言，删除后不会丢失独立语义。例如"save_draft 验证输入、上传文件、写入数据库"应拆为三条——每步对应代码中的一个独立操作，各自可在代码中找到。

**不要跳过前三步直接分类**——未拆分的段落里往往混着多个命题和整体流程，直接归类会导致信息丢失或小节重叠。

## 判定流程

对设计文档中的每条信息，依次执行两步判定。

### 第一步：核对代码是否已反映

依次检查以下四处，任何一处已包含该信息则不需要重复搬运：

- **Python 代码 + docstring** — 函数签名、模块 docstring、函数 docstring
- **Supabase SQL + comment** — RPC 定义、RLS policy、`comment on function`
- **`references/interfaces.md`** — 接口参考文档
- **`SKILL.md`** — AI skill 入口

### 第二步：按归属判断去处

经第一步筛选后，剩余信息按以下规则分配：

**放代码 docstring（贴着实现单元）：**

- 函数自身的行为、约束、边界——"做什么、怎么做、有什么限制"
- 只对阅读/修改/调用该函数的人有意义
- 代码变了这段话也要变
- 依据：`principles/DOCSTR.md`

**放 README（子系统级、跨模块）：**

- 子系统级、跨模块、跨文件的说明
- 脱离目录地图就不容易快速看懂的内容
- 单个函数重写后仍然成立
- 如：模块依赖方向、环境配置、开发测试方法
- 依据：`principles/DOCUMENT_README.md`

**放全局文档（跨 skill、面向未来的设计约束）：**

- 跨 skill 的行为约束或接口契约
- 代码无法自声明的面向未来规则（"以后也必须这样做"）
- 修改一处会影响其他 skill 的规则

**直接删除：**

- 设计决策的"为什么"（业务背景、设计动机）——代码不承载这个
- 从函数签名和实现可直接推断的机械事实
- 已在 `references/interfaces.md` 或 `SKILL.md` 中完整覆盖的调用约定

## 注意事项

### 不要只核对单条，忽略整体流程

- 逐条核对时容易犯的错误：每条信息都能在某处找到，但多条信息组成的**端到端流程**没有在任何一处作为整体写出。
- 例如：save_draft、validate、submit 各自的 docstring 都完整，但"save → validate → submit → 失败回 save 追加版本"这条完整链路分散在三个文件里，没有一处能看到全貌。
- 判断方法：核对完单条后，退一步看整节内容是否描述了一个连贯的流程。如果是，确认这个流程作为整体是否有归宿。

### 设计约束规则 vs 实现描述

- **实现描述**（"现在怎么做"）— 代码已反映的可以删
- **设计约束规则**（"以后也必须这样做"）— 即使代码当前遵循了也不能删，因为代码无法声明面向未来的约束
- **判断方法**：如果删除这条规则后，未来开发者有可能用不同方式实现同样功能，就是约束规则，不能删

### 全局文档 vs README 的边界

- 全局文档放**跨 skill 或面向未来的设计约束**（代码无法自声明、修改一处会影响其他 skill 的规则）。
- README 放**子系统级信息**（开发者在改这个 skill 代码时需要知道的实现细节、数据来源规则）。
- 判断方法：如果这条规则只影响本 skill 内部的开发者，放 README；如果它约束了上下游 skill 的行为或声明了"以后也必须这样"的原则，放全局文档。

### 小节拆分要检查正交性

- 拆完命题后要检查同一文档内各小节之间是否正交：每个小节只回答一个维度的问题，不重叠。
- 例如「定位」回答"是什么 + 做什么"，「边界」回答"不做什么 + 上下游分工"——如果边界中出现了自身能力描述，说明混入了定位内容，需要移走。
- 检查方法：读完每个小节，用一句话概括它的维度；如果两个小节的概括维度有交集，就需要重新拆分。

### 同一规则不要拆进两个小节

- 如果一条规则在小节 A 和小节 B 中都有表述（即使措辞略有不同），选择归属更自然的那一个小节，另一个只保留引用或不写。
- 重复表述会导致后续维护时只改一处、另一处过时。

### 不知道放哪儿就先放 README

- 搬运时归属不明确的内容，先放 README，后续整理时再决定是否迁移到全局文档或 references。

## 排版规则

- 每条规则独立一行 bullet，一句一规则。

## 典型判例

| 情况 | 处理 | 原因 |
|------|------|------|
| 函数签名、参数、返回值 | 删除 | 代码自解释 |
| 模块级职责（一句话） | 删除 | 模块 docstring 已有 |
| 模块间依赖方向 | → README | 跨模块，代码 import 可推断但没有显式声明规则 |
| Storage 路径格式约定 | → docstring | 贴着 storage.py 的约束 |
| 函数执行步骤（3-5 步） | 删除 | 代码读下来就是这些步骤 |
| 调用约定"先调 A 再调 B" | 删除 | `references/interfaces.md` 已写 |
| 业务场景"什么时候用" | 删除 | 设计动机，代码不承载 |
| RLS policy 名称和设计 | 删除 | SQL 侧注释已有 |
| 环境变量和测试配置 | → README | 开发者上手需要，跨文件 |
| 文件路径准源 | → README | 子系统级实现细节，不影响其他 skill |
| "所有数据库操作必须走 RPC"（代码已遵循） | → 全局文档 | 设计约束规则，代码无法自声明面向未来约束 |
| 端到端流程（各步骤 docstring 完整但无整体视图） | → README | 跨模块流程，需作为整体记录 |

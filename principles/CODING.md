# neoskills 编码规范

本文档是本仓库编码规则的唯一事实来源。所有代码实现、重构和评审默认以本文件为准。
沟通方式、文档协作和项目流程仍以 `AGENTS.md` 为准；若出现冲突，以本文件处理编码问题，
以 `AGENTS.md` 处理协作问题。

适用范围：Python 代码与脚本、YAML / JSON / schema 结构，以及 skill 代码与目录组织。

## 编码规则

### 1. 使用 `uv` 管理 Python 依赖

- Python 项目的依赖管理、环境同步和执行流程优先使用 `uv`
- 除非目标模块存在不可替换的工具链约束，否则不要混用 `pip`、`poetry`
- 新增工具链例外时，必须在设计或说明文档中写明原因

### 2. 函数式编程优先

- 优先使用独立函数，不要为了组织代码引入状态型类
- 函数应尽量做到同输入同输出，避免依赖隐式共享状态
- 不要在函数内部修改传入的列表、字典；需要变更时返回新对象
- 能组合小函数解决的问题，不要用继承层级包装
- 工具函数应独立存在，避免把简单能力埋进状态型对象内部

### 3. 先划清 I/O 边界，再写业务逻辑

- 读文件、写文件、网络请求、调用外部进程都属于 I/O
- I/O 函数负责“拿数据”和“落数据”；业务函数负责“变换数据”
- 行为变更优先拆成“读取 -> 转换 -> 写回”三个阶段，避免在一个函数里混杂

### 4. 批量操作优先于循环中的 I/O

- 一次读取后完成一组修改，再一次写回
- 避免在循环里反复读写同一个文件、同一个文档对象或同一个远端接口
- 如果任务天然是批处理，API 设计就要支持批处理

### 5. 数据结构保持扁平

- YAML / JSON 结构优先不超过 2 层嵌套
- 能通过字段区分类型时，不要再人为增加一层顶级分组
- 避免使用 `fields`、`items`、`data` 这类缺乏语义的包裹层

### 6. 模块保持高内聚、低耦合

- 一个模块只处理一类对象或一类职责
- 模块名必须直接表达职责，不要默认落到 `utils.py`、`tools.py`
- 优先按操作对象或职责拆分模块
- 当一个模块同时承担多类数据处理和校验逻辑时，通常已经该拆分

### 7. 删除冗余代码

- 只有“额外语义”才值得包装；单纯转发调用不算抽象
- 相似函数优先合并为一个可配置函数
- 标准库或成熟库已经解决的问题，不要重复实现

### 8. 默认值显式常量化

- 默认值定义为模块级常量，不要散落在函数体里
- 常量命名使用清晰语义，推荐 `DEFAULT_` 前缀
- 用户输入或配置可以覆盖默认值，但默认值本身必须集中定义

## Skill 开发补充规则

### 1. 遵循统一 skill 结构

- skill 目录默认使用 `skills/<skill_name>/`
- `SKILL.md` 放在 skill 根目录，执行脚本放在 `scripts/` 子目录
- 测试样本、预期输出和测试临时输出必须分目录管理，避免把一次性产物混进源码目录

### 2. 命名必须可被 Python 模块系统稳定消费

- skill 目录名和 Python 模块名必须使用下划线命名
- 禁止使用连字符命名 skill 目录或模块
- 新增命名规则例外前，先确认不会影响导入路径、脚本引用和测试发现

### 3. Skill 元数据必须完整

- `SKILL.md` 必须包含最基本的元数据，至少保证 `name` 和 `description` 可用
- skill 结构调整后，必须同步更新相关脚本入口、说明文档和测试引用

### 4. 创建或修改 SKILL.md 时必须调用 skill-creator

- 新建 skill 或修改已有 `SKILL.md` 时，通过 `skill-creator` 操作，不得手动编写
- 详见 `principles/SKILL.md`

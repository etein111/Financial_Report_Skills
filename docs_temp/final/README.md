## 整理文档核心原则

> 正确定义，唯一归属，引用而非复制。

- **唯一事实源**
  每条规则只在一个地方定义，其他地方通过引用指向它。
- **正交性**
  每个文档覆盖一个独立的关注点，文档之间不重叠。两个文档触及同一话题时，一个是权威定义，另一个是引用者。
- **规则与规格并重**
  文档陈述 WHAT 和 WHY（规则、约束、原因），同时保留必要的 HOW（算法、数据来源、处理方式）。具体 RPC 名、bucket 名、代码路径等纯技术细节不记录；但决定系统能否实现的规格细节（如 SFC 官网查询地址、相似度算法）必须保留，否则规则无法落地。
- **分层归属**
  内容放到职责最匹配的位置。跨项目全局准则（换一个项目仍然适用）放 `principles/`，本项目具体规范放本目录。
- **合并不丢信息**
  内容搬迁到目标文档时，源文档的每条规则都必须在目标文档中有对应。
- **内容优于元信息**
  文档就是内容本身，不是关于内容的计划。起草过程的痕迹（编号、待定标记、文件定位描述）是噪声，应清理。
- **命名一致性**
  所有文档对同一概念使用相同名称。命名规则见 `architecture.md`。
- **边界讨论**
  当资料内容不属于现有任何文档的范围，或无法判断归属时，必须先讨论再处理。

## 整理文档实操规则

以下规则来自文档整理实践，随整理过程持续补充。

- **规则必须说清业务背景**
  每条规则先讲「为什么存在」（业务问题、合规要求），再讲「怎么做」。只列步骤不讲原因的规则无法被正确理解和执行。
- **先理清概念再整理**
  整理前确认源文档的概念模型是否正确：
  - 混淆概念以 seed 数据等权威源为准修正。
  - 遗漏分类补全后再整理。
  - 无法确认时停下来向用户提问，不假设。
- **相同要求合并，总结用大白话**
  - 多个分类具有相同规则时合并为一列或一组。
  - 表格下方的补充规则用自然语言逐条总结，一行一条。
  - 总结必须比表格本身更易读，不是表格的复述。
- **节顺序跟随读者路径**
  同一文档内的节排序匹配读者的自然阅读路径：
  - 先知道有什么。
  - 再知道怎么操作。
  - 再知道流程怎么流转。
  - 最后是权限控制。
- **独立关注点独立成节**
  - 当一个概念不属于任何现有节时，为其新开一节，不硬塞进相近的节。
  - 节的粒度由关注点的独立性决定，不由内容量决定。
- **未来能力放项目级文档**
  - 尚未确定子系统归属的功能规划放入 overview.md 的 Features 节，不放 TODO.md 暂存。
  - Features 节承载方向性的跨子系统能力规划。
  - TODO.md 只暂存整理过程中无法确定归属的内容片段。
- **标题与详述分开**
  - 规则标题单独一行，详述另起一行缩进。
  - 详述包含多个要点时，每个要点单独一行。
